# نقشه معماری و برنامه اجرایی داشبورد مدیریتی فروش‌یار AI

> وضعیت سند: پیش‌نویس اجرایی برای هم‌راستاسازی معماری و پیاده‌سازی  
> نسخه: 1.0  
> مخزن: `smk1367/Forushyar-AI`  
> شاخه مبنا: `main`

## 1. هدف

هدف، ساخت یک داشبورد مدیریتی فارسی، راست‌چین، واکنش‌گرا، امن و قابل توسعه برای مدیریت یکپارچه کالا، انبار، ارتباط با مشتری، مکالمات، کارکنان، فروش، گزارش‌ها و تنظیمات است.

این سند مبنای طراحی و تقسیم کار است؛ به‌معنای آن نیست که قابلیت‌های ذکرشده هم‌اکنون پیاده‌سازی شده‌اند. هر قابلیت باید با مدل داده، API، مجوز، رابط کاربری، تست و مستندات تحویل شود.

## 2. وضعیت موجود بر اساس کد مخزن

### فناوری‌های موجود
- Backend: Python و FastAPI
- Database: PostgreSQL و SQLAlchemy async
- Migration: Alembic
- Cache / infrastructure: Redis
- Runtime: Docker Compose
- API prefix: `/api/v1`

### قابلیت‌های موجود یا اولیه
- کالا: ایجاد و فهرست کالا
- قیمت: ثبت قیمت و نگهداری تاریخچه قیمت
- انبار: تعریف انبار، مانده، گردش، رسید، حواله، انتقال و رزرو موجودی
- CRM پایه: مشتری، مکالمه و پیام
- AI: مسیر چت با مدل زبانی سازگار با APIهای OpenAI و زمینه اطلاعات محصول/موجودی
- رابط وب: صفحه HTML ثبت کالا در `/admin/products`

### شکاف‌های مهم
- رابط وب فعلی یک پنل جامع مدیریتی نیست.
- کاربر، نقش، مجوز، محدوده دسترسی شعبه/انبار و نشست واقعی کاربر هنوز باید طراحی و پیاده‌سازی شود.
- تخصیص مکالمه به اپراتور، صف، SLA، پیگیری و گزارش عملکرد اپراتور کامل نیست.
- سفارش فروش، اقلام سفارش، فاکتور، پرداخت، برگشت از فروش و مدل جامع رویداد فروش در مدل‌های فعلی دیده نمی‌شوند.
- گزارش مدیریتی باید پس از شکل‌گیری داده‌های عملیاتی فروش تعریف شود، نه بر پایه اعداد ساختگی یا دستی.
- API Key سراسری فعلی برای شروع محلی مناسب است، اما جایگزین هویت و مجوزدهی کاربران در محیط عملیاتی نیست.

## 3. تصمیم‌های معماری

### 3.1 معماری کلان
معماری پیشنهادی در گام نخست یک سامانه ماژولار با Backend یکپارچه (Modular Monolith) است؛ نه مجموعه‌ای از Microserviceهای زودهنگام.

- Frontend مستقل در مسیر `frontend/`
- Backend فعلی FastAPI در مسیر `backend/`
- PostgreSQL به‌عنوان مرجع اصلی داده
- Redis برای cache، rate limiting و صف‌های کوتاه‌مدت
- پردازش‌های زمان‌بر از طریق worker و صف وظایف، در صورت نیاز عملیاتی
- قرارداد API نسخه‌دار و مستند
- رویدادهای دامنه برای اتصال فروش، انبار، مکالمه و گزارش‌ها
- Outbox Pattern برای انتشار مطمئن رویدادهای مهم پس از تثبیت جریان‌های تراکنشی

### 3.2 فناوری پیشنهادی Frontend
- React + TypeScript + Vite
- React Router برای مسیریابی
- TanStack Query برای cache و مدیریت درخواست‌های سرور
- React Hook Form + Zod برای فرم و اعتبارسنجی
- کتابخانه کامپوننت مبتنی بر Radix/shadcn یا طراحی اختصاصی معادل
- CSS variables و design tokens برای یکپارچگی طراحی
- نمودارهای دسترس‌پذیر و قابل چاپ
- پشتیبانی کامل RTL؛ تمام اعداد، تاریخ‌ها و واحد پول باید formatter متمرکز داشته باشند.

انتخاب کتابخانه نهایی باید با lockfile، سازگاری نسخه‌ها، مجوز استفاده و توان نگهداری تیم ثبت شود.

### 3.3 اصول داده و تراکنش
- شناسه داخلی UUID و شناسه نمایشی مستقل برای سفارش/فاکتور/مکالمه
- مبلغ با Decimal/Numeric؛ هرگز float برای پول استفاده نشود.
- زمان ذخیره‌شده در پایگاه داده UTC باشد؛ نمایش مطابق منطقه زمانی سازمان.
- تاریخ شمسی فقط در لایه نمایش/ورودی و با تبدیل معتبر مدیریت شود.
- عملیات تغییردهنده موجودی یا وجه باید تراکنشی و idempotent باشد.
- مانده موجودی از گردش‌های ثبت‌شده قابل تطبیق و بازسازی باشد.
- حذف داده‌های مالی/انبار ممنوع یا محدود به گردش اصلاحی و ثبت دلیل باشد.
- تمام عملیات حساس actor، زمان، نتیجه، شناسه درخواست و دلیل داشته باشند.

## 4. ساختار ناوبری داشبورد

### صفحه خانه / نمای مدیریتی
- فروش امروز، این ماه و مقایسه با دوره قبل
- تعداد سفارش‌های باز، تکمیل‌شده و لغوشده
- ارزش سفارش و میانگین مبلغ سفارش
- موجودی قابل فروش، اقلام کم‌موجود و کالاهای بدون موجودی
- مکالمات باز، منتظر اپراتور و عبورکرده از SLA
- وضعیت صف‌ها و عملکرد کارکنان
- هشدارهای عملیاتی و فعالیت‌های اخیر
- فیلتر تاریخ، شعبه، انبار و کانال

هر کارت آماری باید به صفحه جزئیات با همان فیلترها هدایت شود.

### 4.1 محصولات و انبار
**محصولات**
- فهرست و جست‌وجوی کالا با فیلتر وضعیت، گروه، برند و کد
- ایجاد/ویرایش کالا، تصویر، بارکد، واحد، ویژگی و تنوع
- دسته‌بندی سلسله‌مراتبی و واحدهای قابل تبدیل در صورت نیاز کسب‌وکار
- قیمت جاری، تاریخچه قیمت، بازه اثرگذاری و منبع قیمت
- ورود/خروج Excel یا CSV با preview، اعتبارسنجی و گزارش خطا
- غیرفعال‌سازی به‌جای حذف کالاهای دارای سابقه تراکنش

**انبار**
- داشبورد مانده به تفکیک کالا، انبار و شعبه
- رسید، حواله، انتقال، تعدیل و شمارش دوره‌ای
- رزرو و آزادسازی رزرو
- هشدار نقطه سفارش، حداقل/حداکثر و کالای راکد
- تاریخچه گردش و تطبیق مانده با دفتر گردش
- موجودی قابل فروش = موجودی فیزیکی منهای رزرو معتبر

**قواعد پذیرش**
- هر حرکت موجودی دارای شناسه یکتا و علت باشد.
- موجودی منفی بدون مجوز و سیاست روشن امکان‌پذیر نباشد.
- انتقال بین دو انبار، ثبت خروج و ورود متوازن و قابل ردیابی داشته باشد.
- درخواست تکراری نباید حرکت دوم ایجاد کند.

### 4.2 مکالمات و مرکز ارتباط
- صندوق ورودی یکپارچه با فیلتر کانال، صف، وضعیت و اولویت
- جزئیات مکالمه با timeline پیام‌ها و رخدادها
- تخصیص دستی/خودکار به صف و اپراتور
- وضعیت‌های روشن: جدید، در انتظار، تخصیص‌یافته، پاسخ‌داده‌شده، ارجاع، بسته
- یادداشت داخلی جدا از پیام قابل مشاهده برای مشتری
- برچسب، نتیجه مکالمه، دلیل ارجاع و وظیفه پیگیری
- SLA پاسخ اول و زمان حل
- جست‌وجو بر اساس مشتری، تلفن، شناسه و متن
- ثبت رضایت، سیاست نگهداری و سطح دسترسی برای فایل صوتی/رونوشت
- اتصال تلفنی/SIP به‌صورت integration مستقل و پس از آزمون واقعی زیرساخت

**قواعد پذیرش**
- پیام مشتری و یادداشت داخلی هرگز در یک سطح دسترسی نمایش داده نشوند.
- تغییر مسئول، وضعیت و اولویت در تاریخچه ثبت شود.
- اپراتور فقط مکالمات مجاز بر اساس نقش و صف را ببیند.
- شکست اتصال بیرونی نباید موجب از دست رفتن پیام ثبت‌شده شود.

### 4.3 کارکنان و مدیریت
- فهرست کارکنان و پروفایل
- دعوت، فعال‌سازی، تعلیق و غیرفعال‌سازی حساب
- نقش‌های پیش‌فرض و نقش سفارشی
- مجوزهای ریزدانه بر اساس منبع و عملیات
- محدودیت دامنه دسترسی به شعبه، انبار یا صف
- تاریخچه ورود، نشست‌های فعال و خروج اجباری
- تخصیص صف و برنامه کاری
- شاخص‌های عملکرد با تعریف محاسبات مستند

**مدل مجوز پیشنهادی**
- `users`
- `roles`
- `permissions`
- `user_roles`
- `role_permissions`
- `user_scopes` برای محدودیت شعبه/انبار/صف
- `sessions` یا استفاده از ارائه‌دهنده هویت معتبر
- `audit_events`

مجوز باید در Backend اعمال شود؛ پنهان‌کردن دکمه در Frontend کنترل امنیتی محسوب نمی‌شود.

### 4.4 فروش و گزارش‌های فروش
پیش از گزارش‌گیری کامل، جریان ثبت سفارش باید وجود داشته باشد.

**دامنه داده پیشنهادی**
- `sales_orders`
- `sales_order_items`
- `invoices`
- `invoice_items` در صورت تفاوت ساختار فاکتور با سفارش
- `payments`
- `payment_allocations`
- `sales_returns`
- `sales_return_items`
- `customers`
- ارتباط با رزرو، مصرف موجودی و گردش انبار

**صفحات عملیاتی**
- فهرست سفارش‌ها با وضعیت و مسیر گردش کار
- جزئیات سفارش و تاریخچه تغییرات
- قیمت واحد، تخفیف، مالیات، هزینه و مبلغ نهایی
- ثبت پرداخت و تطبیق با سفارش/فاکتور
- مرجوعی و استرداد با کنترل اثر انبار و وجه
- چاپ/خروجی اسناد با شماره‌گذاری کنترل‌شده

**گزارش‌ها**
- فروش ناخالص و خالص
- تعداد و مبلغ سفارش
- فروش بر اساس کالا، دسته، مشتری، شعبه و کاربر
- تخفیف، برگشت و لغو
- روش پرداخت و وضعیت وصول
- سود ناخالص فقط پس از تعریف و ثبت بهای تمام‌شده معتبر
- خروجی CSV/XLSX و PDF با ثبت فیلترها و زمان تولید

تمام گزارش‌ها باید از داده عملیاتی معتبر یا جدول‌های تجمیعی قابل بازسازی تولید شوند.

### 4.5 تنظیمات
- مشخصات سازمان و شعب
- واحد پول و سیاست نمایش ریال/تومان
- منطقه زمانی، قالب تاریخ و زبان
- شماره‌گذاری سفارش، فاکتور و اسناد انبار
- مالیات و قواعد قیمت‌گذاری
- تنظیمات اعلان‌ها
- تنظیمات AI، مدل، سقف هزینه و سیاست داده
- تنظیمات اتصال تلفنی و کانال‌ها
- مدیریت کلیدهای integration از طریق Secret Manager؛ نه ذخیره secret در مرورگر یا کد
- نگهداری داده، پشتیبان‌گیری، خروجی و سیاست حریم خصوصی
- تنظیمات امنیتی و نشست‌ها

تغییر تنظیمات حساس باید مجوز ویژه، ثبت audit و در موارد لازم تأیید دومرحله‌ای داشته باشد.

## 5. امنیت و حریم خصوصی — مانع انتشار عملیاتی

### اقدام فوری روی مخزن فعلی
1. فرض شود هر secret ثبت‌شده در فایل `.env` در معرض افشا بوده است؛ رمز پایگاه داده، API Key و کلیدهای احتمالی را rotate کنید.
2. فایل‌های `.dump` و آرشیوهای پشتیبان بررسی شوند. در صورت وجود داده واقعی مشتری یا اطلاعات محرمانه، فرآیند پاسخ به رخداد و اطلاع‌رسانی متناسب اجرا شود.
3. فایل‌های محرمانه از نسخه جاری و تاریخچه Git حذف شوند. حذف ساده در یک commit تاریخچه قدیمی را پاک نمی‌کند.
4. از force-push پاک‌سازی‌شده فقط با هماهنگی همه همکاران استفاده شود؛ mirror/cloneهای قدیمی نیز باید مدیریت شوند.
5. `.gitignore` برای `.env*` (با استثنای فایل نمونه)، `backups/`، `*.dump`، `*.tar.gz`، `__pycache__/` و `*.py[cod]` تکمیل شود.
6. پیش از ادامه، repository secret scanning و بررسی دسترسی‌های مخزن انجام شود.

### امنیت معماری مقصد
- OAuth2/OIDC یا ارائه‌دهنده هویت معتبر؛ MFA برای مدیران
- نشست امن با cookieهای HttpOnly، Secure و SameSite یا الگوی استاندارد OIDC
- CSRF protection در صورت استفاده از cookie
- RBAC و scope enforcement در تمام endpointها
- Rate limit و محدودیت تلاش ورود
- TLS، reverse proxy و CORS محدود به originهای واقعی
- ثبت audit برای ورود، خروج، تغییر نقش، قیمت، موجودی، سفارش و تنظیمات
- رمزنگاری backup و انتقال نسخه خارج از میزبان
- سیاست retention، حذف داده و دسترسی به فایل صوتی
- عدم قرار دادن API Key سراسری در localStorage یا sessionStorage مرورگر

تا پیش از تکمیل احراز هویت، مجوزها و پاک‌سازی secrets، داشبورد نباید برای استفاده عمومی عملیاتی منتشر شود.

## 6. قرارداد API

- مسیرهای موجود `/api/v1` حفظ شوند تا سازگاری نسخه فعلی نشکند.
- endpointهای جدید بر اساس منبع دامنه‌ای و با schema درخواست/پاسخ مستقل ساخته شوند.
- برای فهرست‌ها pagination استاندارد، sort whitelist و filter validation اعمال شود.
- برای عملیات مالی/انبار header یا فیلد idempotency اجباری باشد.
- خطاها ساختار قابل پیش‌بینی، کد قابل پایش و پیام امن داشته باشند.
- هیچ منطق تجاری مهمی فقط در مرورگر اجرا نشود.
- مستندات OpenAPI و نمونه درخواست/پاسخ هر endpoint به‌روز باشند.

## 7. طراحی تجربه کاربری

- فارسی و RTL در تمام صفحات، فرم‌ها، نمودارها و جدول‌ها
- منوی کناری قابل جمع‌شدن و breadcrumb
- نوار بالایی شامل جست‌وجوی سراسری، اعلان، پروفایل و انتخاب شعبه
- طراحی responsive برای دسکتاپ، تبلت و موبایل
- وضعیت‌های loading، empty، error، permission denied و success برای هر صفحه
- فرم‌ها با اعتبارسنجی سمت کاربر و سرور
- تأیید صریح برای عملیات برگشت‌ناپذیر یا حساس
- میانبر صفحه‌کلید و رعایت استانداردهای دسترس‌پذیری
- نمایش پول با formatter واحد و برچسب شفاف «تومان» یا «ریال»
- پشتیبانی از تاریخ شمسی در UI و حفظ timestamp استاندارد در API
- عدم استفاده از داده نمایشی به‌عنوان عدد واقعی داشبورد

## 8. برنامه اجرای مرحله‌ای

### مرحله صفر — ایمن‌سازی و تثبیت
- rotate secrets و پاک‌سازی فایل‌های محرمانه/بکاپ از Git history
- بررسی نسخه‌های موجود، dependencyها، migrationها و وضعیت backup
- تعریف روش deploy، health check، log و rollback
- افزودن CI برای lint، type check، تست و بررسی امنیت dependencyها

**معیار خروج:** هیچ secret یا backup حساس در تاریخچه قابل دسترس مخزن نباشد؛ تست‌های پایه و مسیر بازیابی مستند باشند.

### مرحله یک — هویت، مجوز و پوسته داشبورد
- احراز هویت واقعی، نقش‌ها و scope
- audit log و نشست‌ها
- ساخت frontend و design system
- layout، sidebar، routing، error handling و صفحه خانه اولیه

**معیار خروج:** کاربر با نقش‌های متفاوت، فقط منوها و داده‌های مجاز را مشاهده و از طریق API نیز فقط همان عملیات را انجام دهد.

### مرحله دو — محصولات و انبار
- تکمیل CRUD و جست‌وجو و import/export کالا
- صفحات مانده و گردش موجودی
- شمارش، تعدیل، انتقال و هشدار حد سفارش
- تست هم‌زمانی و idempotency

**معیار خروج:** سناریوی کامل ورود کالا تا خروج/انتقال و تطبیق مانده با دفتر گردش موفق باشد.

### مرحله سه — مکالمات و اپراتورها
- صندوق ورودی، تخصیص، صف، برچسب و SLA
- پیام، یادداشت داخلی، timeline و پیگیری
- گزارش کیفیت و عملکرد
- integration تلفنی پس از آزمون مستقل

**معیار خروج:** مکالمه از ورود تا تخصیص، پاسخ، ارجاع و بسته‌شدن قابل ردیابی باشد.

### مرحله چهار — سفارش، فاکتور و پرداخت
- طراحی workflow سفارش
- رزرو/مصرف موجودی متصل به سفارش
- فاکتور و پرداخت با idempotency
- برگشت از فروش و استرداد
- ثبت audit و کنترل مجوز

**معیار خروج:** سناریوی کامل سفارش تا پرداخت، تحویل و برگشت با مانده انبار و گزارش مالی سازگار باشد.

### مرحله پنج — گزارش‌ها و تنظیمات
- داشبورد شاخص‌ها بر اساس داده واقعی
- فیلترهای مشترک، خروجی و گزارش زمان‌بندی‌شده
- تنظیمات سازمان، مالی، ارتباطی و AI
- کنترل دسترسی و تاریخچه تغییر تنظیمات

**معیار خروج:** اعداد گزارش با queryهای مرجع و اسناد عملیاتی تطبیق‌پذیر باشند.

### مرحله شش — آمادگی تولید
- تست بار، امنیت، بازیابی و failover
- observability، alerting و runbook
- بررسی دسترس‌پذیری و مرورگرها
- UAT با نقش‌های واقعی
- انتشار مرحله‌ای و برنامه rollback

## 9. استاندارد Definition of Done

هر قابلیت فقط زمانی «تکمیل» محسوب می‌شود که:
1. مدل داده و migration برگشت‌پذیر/قابل کنترل داشته باشد.
2. API با validation و مجوز سمت سرور پیاده‌سازی شده باشد.
3. رابط کاربری RTL، responsive و دارای حالت‌های خطا و خالی باشد.
4. تست unit و integration برای مسیر موفق و شکست وجود داشته باشد.
5. رویدادهای حساس audit و log قابل ردیابی داشته باشند.
6. مستندات فارسی و OpenAPI به‌روز باشند.
7. تست regression و بررسی امنیتی مربوط اجرا شده باشند.
8. معیار پذیرش کسب‌وکار و نتیجه تست ثبت شده باشد.

## 10. ترتیب اولویت پیشنهادی

## 11. اولین بسته اجرایی پیشنهادی

بسته اول نباید صرفاً یک صفحه زیبا باشد. خروجی آن باید شامل این موارد باشد:
- رفع ریسک امنیتی و ایجاد سیاست secrets
- مدل کاربر/نقش/مجوز و تست‌های مجوز
- اسکلت `frontend/` با React/TypeScript
- layout فارسی و RTL شامل sidebar، header، breadcrumb و route guards
- اتصال امن به API و مدیریت خطا/نشست
- صفحه خانه با کارت‌های متصل به API واقعی یا نمایش صریح حالت «داده هنوز موجود نیست»
- CI پایه برای lint، typecheck و تست‌های frontend/backend

پس از این بسته، ماژول محصولات و انبار به‌عنوان نخستین قابلیت end-to-end تکمیل می‌شود.
