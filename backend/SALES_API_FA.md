# ماژول فروش: پیش‌فاکتور، سفارش و پرداخت

این ماژول از API نسخه ۱ و احراز هویت موجود با هدر X-API-Key استفاده می‌کند. قبل از استفاده، migrationها را اجرا کنید:

~~~bash
make migrate
~~~

## گردش کار

1. پیش‌فاکتور با وضعیت DRAFT ساخته می‌شود. قیمت و مشخصات مشتری/کالا در سند snapshot می‌شوند.
2. با POST /api/v1/sales/quotes/{id}/send سند به وضعیت SENT می‌رود.
3. با POST /api/v1/sales/quotes/{id}/convert پیش‌فاکتور به سفارش تبدیل می‌شود. رزرو همه اقلام و تغییر وضعیت پیش‌فاکتور در یک تراکنش واحد انجام می‌شود.
4. سفارش مستقیم نیز با POST /api/v1/sales/orders قابل ثبت است. سفارش در حالت AWAITING_PAYMENT ایجاد می‌شود و موجودی همان‌جا رزرو می‌شود.
5. پرداخت با POST /api/v1/sales/orders/{id}/payments به حالت PENDING ثبت می‌شود. تأیید پرداخت فقط با POST /api/v1/sales/payments/{payment_id}/confirm انجام می‌شود.
6. بعد از پرداخت کامل، سفارش CONFIRMED می‌شود. ارسال با /orders/{id}/ship موجودی فیزیکی و رزروشده را هم‌زمان کسر می‌کند؛ سپس /orders/{id}/deliver تحویل را ثبت می‌کند.
7. لغو سفارش پرداخت‌نشده با /orders/{id}/cancel رزرو را آزاد می‌کند. لغو سفارش دارای پرداخت تأییدشده مسدود است تا استرداد وجه بدون گردش حساب انجام نشود.

## APIها

تمام مسیرها نیازمند هدر X-API-Key هستند.

| Method | Path | توضیح |
|---|---|---|
| POST | /api/v1/sales/quotes | ایجاد پیش‌فاکتور |
| GET | /api/v1/sales/quotes | فهرست پیش‌فاکتورها |
| POST | /api/v1/sales/quotes/{id}/send | ارسال/نهایی‌کردن پیش‌فاکتور |
| POST | /api/v1/sales/quotes/{id}/convert | تبدیل به سفارش و رزرو اتمیک |
| POST | /api/v1/sales/orders | ایجاد مستقیم سفارش و رزرو اتمیک |
| GET | /api/v1/sales/orders | فهرست سفارش‌ها |
| GET | /api/v1/sales/orders/{id} | جزئیات سفارش و تاریخچه |
| POST | /api/v1/sales/orders/{id}/payments | ثبت پرداخت در انتظار تأیید |
| POST | /api/v1/sales/payments/{id}/confirm | تأیید پرداخت |
| POST | /api/v1/sales/orders/{id}/cancel | لغو سفارش و آزادسازی رزرو |
| POST | /api/v1/sales/orders/{id}/ship | ارسال و کسر موجودی |
| POST | /api/v1/sales/orders/{id}/deliver | ثبت تحویل |

## نمونه ایجاد پیش‌فاکتور

شناسه مشتری، انبار و کالا را از APIهای موجود /api/v1/customers، /api/v1/warehouses و /api/v1/products بگیرید. اگر unit_price ارسال نشود، قیمت فعال کاتالوگ با همان currency_code استفاده می‌شود. مقدار پولی این نسخه پیش‌فرض IRT (تومان داخلی برنامه) است.

~~~json
{
  "customer_id": "00000000-0000-0000-0000-000000000010",
  "warehouse_id": "00000000-0000-0000-0000-000000000020",
  "currency_code": "IRT",
  "tax_rate": "9.00",
  "header_discount": "0.00",
  "expires_in_days": 7,
  "idempotency_key": "quote-client-000001",
  "lines": [
    {
      "product_id": "00000000-0000-0000-0000-000000000030",
      "quantity": "2.000",
      "discount_amount": "0.00"
    }
  ]
}
~~~

## نمونه ثبت پرداخت

~~~json
{
  "payment_method": "BANK_TRANSFER",
  "amount": "250000.00",
  "idempotency_key": "payment-client-000001"
}
~~~

تأیید پرداخت نیازمند دلیل ثبت و در صورت وجود، شناسه پیگیری معتبر است. API این نسخه تأیید را به‌صورت دستی و توسط دارنده کلید API مجاز می‌کند؛ اتصال خودکار به درگاه و webhook بانکی در دامنه این تغییر نیست.

## تضمین‌ها و محدودیت‌ها

- رزرو چندقلمی با قفل‌گذاری ردیف موجودی در ترتیب ثابت شناسه کالا انجام می‌شود؛ اگر یک قلم موجودی کافی نداشته باشد، کل تراکنش rollback می‌شود.
- کلیدهای تکرارپذیری روی پیش‌فاکتور، سفارش و پرداخت یکتا هستند؛ استفاده مجدد از همان کلید با payload متفاوت، خطای 409 می‌دهد.
- محاسبات پولی با Decimal و دو رقم اعشار انجام می‌شود؛ مقدار کالا سه رقم اعشار دارد.
- قیمت، SKU، نام کالا، نام مشتری و نام انبار در سند snapshot می‌شوند.
- تحویل از سفارش SHIPPED ثبت می‌شود؛ موجودی در زمان ارسال از دفتر انبار کسر شده است.
- این نسخه گردش استرداد وجه، اتصال درگاه آنلاین، سطح دسترسی تفکیکی اپراتورها و صدور PDF/فاکتور مالیاتی را پیاده‌سازی نمی‌کند.
